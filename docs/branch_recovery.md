# 分支与数据恢复手册

本文覆盖两类「出问题之后怎么办」：

1. **Git 层面**：误操作、提交信息事故、分支丢失的判定与恢复流程（主要部分）；
2. **应用层面**：程序异常退出后的笔记、工作区与图片索引恢复。

原则：**先判定真实状态，再决定动作**。不要凭终端显示（尤其是乱码）推断存储已损坏，
也不要在未确认状态前反复执行改写历史的操作。

## 1. Git 误操作恢复

### 1.1 通用判定步骤

任何「提交看起来不对劲」的场合，按顺序执行：

```bash
git status                          # 工作区与暂存区状态
git log --oneline -10               # 最近提交
git cat-file commit <hash>          # 查看提交对象的原始字节
git reflog                          # 本分支与 HEAD 的完整移动历史
```

- `git reflog` 是恢复的最后底牌：只要提交过（甚至只是曾 `git add` 到被 reset 的提交），
  对象默认在 reflog / gc 有效期内都可找回。
- 判定「存储 vs 显示」：中文提交信息在终端显示为乱码，多数是**终端编码问题而非存储
  损坏**。用 `git cat-file commit <hash>` 查看原始字节，或用能按字节读取的脚本验证；
  确认字节正确就不要 amend / 重做，否则是在制造真实损坏。

### 1.2 提交信息写错（最常见）

本仓库的真实事故模式：

| 事故 | 成因 | 恢复 |
| --- | --- | --- |
| 提交信息开头出现 `锘?` / BOM 字符 | 用 PowerShell `Set-Content -Encoding utf8` 写提交信息文件（带 BOM）再 `commit -F` | 未推送：`git commit --amend -F <无 BOM 文件>`；已推送：见 1.4 |
| 整条 shell 命令变成了提交信息 | 在 `git commit -m "..."` 里嵌套了多行字符串或复杂命令 | 同上，amend 换成正确信息 |
| 中文显示乱码 | 终端按 GBK 解码 UTF-8 输出 | **不是事故**。确认 `git cat-file` 字节正确后不要动提交 |

预防：提交信息先写入临时文件（UTF-8 **无 BOM**），再 `git commit -F <file>`；
绝不在 `-m` 参数里拼多行字符串；不要用 PowerShell 管道 / 重定向读取 git 输出做验证
（会把 UTF-8 字节流按系统代码页读成乱码，导致误判存储损坏）。

### 1.3 撤销未推送的错误提交

- **只改最后一条提交的信息**：`git commit --amend -F <file>`。
- **提交内容错了但还想保留改动**：`git reset --soft HEAD~1`（改动回到暂存区），修好
  后重新提交。
- **彻底丢弃最后一条提交及其改动**：`git reset --hard HEAD~1`——危险操作，执行前确认
  没有只存在于该提交中的工作；不确定时先用 `git reset --soft` 或建备份分支
  `git branch backup-<date>`。
- **误提交了不该提交的文件**：未推送时 `git reset --soft HEAD~1` 后从暂存区移除再重新
  提交；已推送时用 `git revert` 生成反向提交，不要改写历史。

### 1.4 已推送的错误提交

- **默认用 `git revert <hash>`**：生成反向提交，历史保持线性，对协作者无影响。
- **禁止对主分支 / 共享分支 force push**。个人特性分支确需改写历史（如 rebase 整理）
  时，先确认无他人基于该分支工作，且 force push 需要明确授权。
- 提交被 revert 后又需要其内容：重新 cherry-pick / 重新实现，不要试图「删掉 revert」。

### 1.5 分支与提交找回

```bash
git reflog                          # 找到目标动作前的 HEAD 位置
git branch recover-<date> <hash>    # 把悬空提交钉回一个新分支
git checkout recover-<date>
```

- `git reset --hard`、被强推覆盖、误删分支（`git branch -D`）后的提交，都能从 reflog
  找回；找回后先检查内容再合并回工作分支。
- 合并 / 变基中途想放弃：`git merge --abort` / `git rebase --abort`，回到操作前状态。
- 误删未合并分支前如果只记得分支名：`git reflog | grep checkout` 可定位它最后的提交。

### 1.6 工作区文件误改 / 误删

- **改动未提交**：单文件恢复到最近提交版本 `git checkout -- <file>`（会丢弃该文件
  未提交改动，先确认）；或先 `git stash` 存一份再操作。
- **文件已提交但后来被删**：`git checkout <hash> -- <path>` 从任意历史提交恢复。
- 本仓库的 `tests/` 目录不入库——**git 找不回测试文件**，删除即永久丢失，删除前须确认。

## 2. 应用层数据恢复

### 2.1 笔记文件

- 笔记写入采用同目录临时文件 + 原子替换，崩溃 / 断电**不会留下半写文件**：要么是旧
  内容，要么是完整的新内容。
- 程序异常退出后重新启动，按提示查看崩溃日志；未保存的改动以自动保存的恢复点为准
  （自动保存只用于异常恢复，不替代手动保存）。
- 会话恢复：重启后会尝试恢复上次打开的标签页与分屏布局；个别未保存标签可能丢失，
  以「关闭前保存」为准。

### 2.2 图片与索引

- 图片断链（在资源管理器里移动了 `.md` 而没带 `PanzerNote_assets/`）：用
  「工具 → 恢复缺失的图片...」。恢复只移动 / 复制图片文件，不改动 Markdown 内容；
  证据不足的候选会列入「需人工处理」，不会猜测。
- 图片索引（用户数据目录 `data/config/image_assets.json`）**只是线索**，可删除并
  自动重建；真正的工作状态始终是 Markdown 与文件系统本身。
- 「迁移旧图片目录」用「复制 → 校验 → 删除源」的方式搬移，任一步失败都保留原文件，
  不会出现两边都没有的状态。

### 2.3 备份策略（最重要的恢复手段）

- 定期备份**整个用户数据目录**（笔记 + 设置 + 工作区状态 + 游戏存档 + 图片索引），
  不要只备份单个 JSON 文件；升级或手动迁移前先整体备份一次。
- 程序不提供加密；备份介质的访问权限自行管理。
